# Backend Failure, Concurrency & Integration Testing

This document details how to verify database failure modes, transaction rollbacks, concurrency locks, security token attacks, and full HTTP E2E lifecycles.

---

## 1. Concurrency & Lock Order Testing (`test_delivery_concurrency_locks.py`, `test_delivery_patching.py`, `test_delivery_immutability.py`)

To verify that the ADR-0003 row locking order (`Match -> Innings`) prevents deadlocks:
- **Test Pattern**: Simulate concurrent requests attempting to update the same match and innings using `asyncio.gather()`.
- **Assertion**: Both transactions complete sequentially without deadlock or state corruption.
- **Verification**: Ensure SQL statements generated by SQLAlchemy include `FOR UPDATE` in the expected sequence:
  ```python
  # Verify lock acquisition order
  match = await session.execute(select(Match).where(Match.id == match_id).with_for_update())
  innings = await session.execute(select(Innings).where(Innings.id == innings_id).with_for_update())
  ```

## 2. Transaction Rollback & Failure Recovery Testing

To ensure that failed requests leave no half-saved records:
- **Test Pattern**: Force an unhandled failure or domain exception halfway through an operation (e.g. after adding a delivery but before updating innings score).
- **Assertion**:
  ```python
  # Ensure nothing persisted after exception
  deliveries = (await session.execute(select(Delivery).where(Delivery.innings_id == innings.id))).scalars().all()
  assert len(deliveries) == 0  # Rolled back cleanly
  ```

## 3. Security, Token Rotation & Replay Attack Testing (`test_auth_and_access_e2e.py`)

Security mechanisms must be tested against malicious and unexpected access attempts:

| Attack Scenario | Test Verification |
|---|---|
| **Replayed Refresh Token** | When a previously revoked refresh token is sent to `/auth/refresh`, the system must detect the reuse attack, reject with `401 Unauthorized`, and revoke **all** active refresh sessions for that user. |
| **Expired Token Access** | Send expired JWT in `Authorization: Bearer <token>`. Verify response is `401 Unauthorized` with `WWW-Authenticate: Bearer` header. |
| **Privilege Escalation** | A user with role `viewer` attempts to call `POST /deliveries/...`. Verify response is `403 Forbidden` (`AccessDeniedError`). |
| **Tampered Match Parameter** | Missing or non-integer match ID in path parameter. Verify `require_match_access` fails closed with `400 Bad Request`. |

## 4. Full Match Lifecycle E2E Integration Testing (`test_match_lifecycle_e2e.py`)

The complete match lifecycle exercises the entire FastAPI stack from start to finish:
1. `POST /api/v1/teams/`: Create Team India and Team Australia.
2. `POST /api/v1/players/`: Create 15 players for each team.
3. `POST /api/v1/matches/`: Schedule T20 match between the teams.
4. `POST /api/v1/squads/{id}`: Submit Playing XI, captain, and keeper for both teams.
5. `POST /api/v1/matches/{id}/toss`: Record toss result (India won toss, elected to bat).
6. `POST /api/v1/innings/{id}/start`: Start Innings 1 with opening batters and bowler.
7. `POST /api/v1/deliveries/{id}/1`: Record deliveries until Innings 1 completes.
8. Verify match transitions to `innings_break` with target score set.
9. `POST /api/v1/innings/{id}/start`: Start Innings 2.
10. `POST /api/v1/deliveries/{id}/2`: Score Innings 2 until target reached.
11. `GET /api/v1/scorecards/{id}`: Verify winner, margin, final batting scorecards, and bowling figures.
